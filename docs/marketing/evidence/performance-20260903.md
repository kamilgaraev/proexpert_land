## Причины и приоритет исправления

### P1. Статические CSS и JS передаются без сжатия

Все 13 загруженных файлов CSS/JS из `/assets/` вернулись без `Content-Encoding` даже при `Accept-Encoding: gzip, deflate, br`. Подтверждение совпадает в GET, HEAD и в network-записях Chrome: transfer size практически равен размеру ресурса. HTTP/2 работает; HTML сжат, поэтому проблема конкретно в доставке статических ресурсов.

| Ресурс | Размер содержимого | gzip level 6 тех же байтов |
| --- | ---: | ---: |
| `_default.page.server-ZBrurhiI.css` | 181 327 Б | 24 918 Б |
| `HomePage-CpXQPWfg.css` | 43 420 Б | 7 958 Б |
| `chunk-CrGzeGP9.js` | 344 382 Б | 70 143 Б |
| `_default.page.client-CWUByw_S.js` | 172 293 Б | 54 709 Б |
| Все 13 CSS/JS | 1 137 143 Б | 281 337 Б |

Локальное сжатие неизменённых публичных ресурсов показывает возможность уменьшить их передачу на 855 806 байт (75,3%). Это оценка байтов, не обещание конкретного нового Lighthouse score. Brotli для тех же ресурсов даёт 238 392 байта; для первичного исправления достаточно доступного штатного gzip.

Точечное действие: установить фактическую цепочку раздачи `/assets/` на marketing-хосте и добавить согласованное сжатие text/css и application/javascript с корректным `Vary: Accept-Encoding`. Если ресурсы отдаёт Node через reverse proxy, допустимо подготовить сжатые артефакты при публикации и выбирать вариант в серверном обработчике; если Nginx раздаёт их напрямую, исправление должно действовать в его конфигурации. Сохранить существующий годовой immutable-кеш хешированных файлов. Заголовок `Server: nginx/1.24.0 (Ubuntu)` сам по себе не устанавливает, кто формирует тело ответа. Фактическая production-конфигурация этим аудитом не читалась и не менялась.

DNS-проверка 03:47 МСК: `1мост.рф` → `89.169.44.115`, `api.1мост.рф` → `89.169.44.117`; AAAA главной не обнаружена. Поэтому конфигурация на доступном read-only API-хосте `.117` не доказывает устройство раздачи marketing на `.115`.

Проверка результата: GET с `Accept-Encoding: gzip` возвращает `Content-Encoding: gzip`, декодированные байты идентичны исходным, обычный клиент без поддержки сжатия получает исходный ресурс. После выкладки — один повтор пары Lighthouse.

### P1. Общие стили и вложенная загрузка Google Fonts блокируют первый показ

На главной загружаются два CSS сайта: 181 КБ общего файла и 43 КБ файла страницы. Lighthouse считает неиспользованными на стартовом viewport 95,83% общего CSS (173 774 Б) и 44,43% CSS страницы (19 292 Б). Это не означает, что эти правила можно удалить из приложения: оценка относится только к этому экрану и состоянию.

Цепочка запросов: HTML → `_default.page.server-ZBrurhiI.css` → Google Fonts CSS для IBM Plex Sans и IBM Plex Mono → три файла Sans WOFF2, суммарно 92 318 Б передачи. Отдельный запрос Mono CSS выполнен, но Mono WOFF2 в стартовой загрузке отсутствует. В mobile отчёте модель оценивает возможную экономию FCP на блокирующих запросах в 2950 мс; эту оценку нельзя складывать с другими opportunity savings.

Локальные источники через Gortex:

- `src/renderer/PageShell.tsx:5` безусловно импортирует общий `index.css`.
- `src/index.css:1–2` содержит два внешних `@import` Google Fonts, затем общий Tailwind.
- `src/renderer/_default.page.server.tsx` рендерит публичную страницу внутри той же `PageShell`.

Точечное действие после исправления доставки: убрать вложенные внешние font-CSS запросы из критического CSS, поставлять необходимые Sans WOFF2 с контролируемой локальной загрузкой и сохранить текущую гарнитуру. Проверить фактически используемые алфавиты/начертания перед сокращением. Выделить минимальные базовые стили marketing-оболочки; стили кабинета и редко используемых страниц не включать в начальную CSS-группу главной. Не удалять автоматически правила по Lighthouse coverage.

Критерий: начальный HTML/стили главной больше не тянут общий CSS кабинета и внешние `@import`; текст, меню, форма и другие публичные страницы выглядят прежним образом на desktop/mobile, CLS не ухудшен.

### P2. Публичная оболочка скачивает приватные зависимости

Главная передаёт 915 830 Б JS, 11 запросов. Lighthouse оценивает 328 794 Б как неиспользованные при старте. Среди загруженных ресурсов:

- `chunk-Bb3sP8V1.js`: 72 200 Б содержимого, около 89,6% не использовано; в публичном ресурсе присутствует код Laravel Echo / уведомлений.
- `chunk-bZ00P9al.js`: 76 605 Б содержимого; Lighthouse измеряет около 79,1% неиспользованного JS в своей области покрытия; ресурс содержит код permissions и API.

Причина на уровне границы модулей: `PageShell.tsx:2–3` статически импортирует `AuthProvider` и `PermissionsProvider` до проверки публичного маршрута; `AuthContext.tsx:13` импортирует `disconnectEcho`, а `PermissionsContext.tsx:2–4` — менеджер прав и API. Публичная ветка не монтирует эти providers, но их статические зависимости остаются в загружаемой общей группе. Это доказательство лишней загрузки кода, а не утверждение о запуске приватных запросов: network-аудит не показал API-запросов в этом сценарии.

Точечное действие: выделить публичную оболочку/entry без статических импортов приватных провайдеров; подгружать приватную оболочку на маршрутах кабинета с сохранением SSR/hydration контракта. Проверить вход, восстановление сессии и переходы между публичной и приватной частями. Не заменять это массовой мемоизацией компонентов: TBT сейчас 121 мс mobile и 17,5 мс desktop, основной ущерб — лишний начальный трафик.

### P2. Иллюстрации без Cache-Control

Четыре WebP-изображения в mobile аудите имеют cache TTL 0, суммарно 157 576 Б с заголовками. HEAD главного изображения подтверждает наличие ETag/Last-Modified и отсутствие Cache-Control. Хешированные CSS/JS уже кешируются на год.

Точечное действие: установить политику кеширования версионированных marketing-изображений с явным правилом смены URL при обновлении. Нельзя назначать immutable на неизменяемые по имени URL, если процесс публикации продолжает перезаписывать их содержимое. Это улучшение повторных посещений, не основная причина холодного mobile FCP.

### P3. Мелкие замечания без отдельного рефакторинга

- Lighthouse отмечает forced reflow около 94 мс в `chunk-DsqGI9U3.js:1:3887`. Фрагмент соответствует проверке `window.scrollY` внутри утилит SSR-router. Не следует приписывать эти 94 мс scroll-анимации HomePage без отдельного взаимодействия и профилирования.
- Image delivery предлагает 114 КБ экономии, но сравнивает CSS-размеры изображений. Mobile использует DPR 1,75 и увеличение hero до 120% ширины; уменьшение исходника до ширины CSS может ухудшить чёткость. Уже выбранные WebP и responsive variants сохранять до визуальной проверки. Это не первый приоритет.
- CLS 0 / 0,00292 не указывает на значимую проблему стабильности в стартовом сценарии. Прокрутка, длинные интеракции и полевой INP этим navigation-аудитом не измерялись.
