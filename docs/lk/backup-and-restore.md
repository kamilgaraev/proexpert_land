# Резерв ЛК перед редизайном

Резерв создаётся после приёмки маркетинга и до изменения интерфейса кабинета. Он сохраняет опубликованные файлы ЛК, а не базу данных, пользовательские документы или API. Эти данные редизайн не переносит и не откатывает.

## Штатные операции

В workflow `deploy.yml` предусмотрены цели:

- `backup-lk`: один раз сохраняет текущий выпуск; если резерв уже существует, проверяет его без перезаписи.
- `verify-lk-backup`: проверяет SHA-256, распаковывает архив во временный каталог, проверяет index.html/assets и сравнивает распакованные файлы с архивом. Действующий выпуск не переключается.
- `restore-lk-backup`: требует `confirm_restore=RESTORE-LK-20260904`; проверяет архив, распаковывает отдельный выпуск и атомарно переключает current. При ошибке проверки после переключения возвращает прежнюю ссылку. После операции требуется браузерная проверка входа и основного экрана.

Все операции используют ту же очередь concurrency, что публикация сайта/ЛК, поэтому не выполняются одновременно с деплоем. Маркетинг и API не переключаются. Резерв лежит вне каталога releases и не попадает под очистку старых выпусков.

## Пути

- Текущий выпуск: `/var/www/prohelper_lk/current`.
- Выпуски: `/var/www/prohelper_lk/releases`.
- Резерв: `/var/backups/most-lk/before-redesign-20260904`.
- В резерве: `release.tgz`, `SHA256SUMS`, `original-release.txt`, `created-at.txt`.

Исходный путь обязан находиться внутри каталога выпусков ЛК. Создание архива сравнивает его с исходным выпуском, затем отдельно проверяет распаковку. Пробное переключение production ради проверки не выполняется.

## Текущее доказательство

Workflow подготовлен; YAML разобран, все встроенные shell-команды прошли `bash -n`. Gortex staged review APPROVE, конкретных замечаний нет. Фактическое создание архива, его размер, SHA-256 и run URL должны быть записаны сюда после успешного запуска. До этого резерв нельзя считать созданным и начинать изменение UI ЛК нельзя.
