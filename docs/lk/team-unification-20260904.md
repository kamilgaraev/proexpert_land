# Единая команда МОСТ

Дата: 4 сентября 2026 года. Статус: исследование завершено частично, реализация не принята.

## Требование

В организации работают сотрудники с разными ролями. Разделение на «Администраторов» и «Пользователей» не соответствует продуктовой модели. Основной экран должен содержать один список сотрудников; приглашения и доступы — связанные сценарии этого раздела.

## Подтверждённая причина

- AdminsPage получает adminPanelUsers отдельно от useUserManagement.getOrganizationUsers.
- GET /user-management/organization-users направлен в OrganizationUserController.index; метод пуст. Остальные CRUD-методы этого контроллера также пусты, а отдельные указанные маршрутом методы отсутствуют. Пустой результат нельзя считать отсутствием сотрудников.
- GET /adminPanelUsers фильтрует сотрудников по ролям, разрешённым для интерфейса. Это не полный состав организации.
- GET /users в Landing UserController.index тоже возвращает getAdminsForCurrentOrg, поэтому механическая смена URL не решает проблему.
- UserRepository.paginateInOrganization уже ограничивает выборку членством в organization_user, поддерживает фильтры и пагинацию. Однако текущая предзагрузка organizations и assignedProjects не ограничена текущей организацией; нельзя без проверки выдавать такие отношения наружу.

## Целевой контракт

Один серверный список по членству в текущей организации, с серверной пагинацией и поиском, без исключения прорабов и сотрудников мобильного приложения. Роли и доступы показываются атрибутами сотрудника. Проверки permissions и organization context обязательны. Данные других организаций и проектов не возвращаются. Ошибки загрузки отличимы от пустого списка.

Операции редактирования, блокировки, удаления доступа и назначения ролей необходимо проверить отдельно: существование маршрута не доказывает реализацию. Нельзя переиспользовать пустые обработчики. Доступность действий определяется фактическими правами; владельца защищают серверные ограничения.

## Интерфейс

Один список «Сотрудники», вкладка приглашений, доступ к настройке ролей. Общие компоненты кнопок, полей, вкладок, диалогов и пустых состояний. Форма приглашения и вложенные редакторы должны соответствовать той же дизайн-системе. Число сотрудников берётся из серверной пагинации, а не из длины загруженной страницы. Обновление поиска сбрасывает страницу. Мобильный экран сохраняет имена, роль и доступные действия без горизонтального переполнения.

## Проверки до приёмки

Сотрудники с доступом к ЛК и только к работе с объектами/мобильному интерфейсу видны в одной команде. Изоляция организаций, несколько ролей, длинные имена, пустой результат поиска, ошибка API, повторный запрос, пагинация, ограничения владельца, отсутствие прав на изменение. UI проверяется в собственной встроенной вкладке, письма и реальные изменения прав для визуальной проверки не выполняются.

## Незавершённые изменения

В AdminsPage локально переработана композиция строк прежнего списка. Это промежуточная работа: она не исправляет описанный контракт и не должна выпускаться как готовая единая команда.
