# Инструкции репозитория сайта, лендингов и личного кабинета МОСТ

## Область действия

- Эти правила действуют во всём репозитории. Более вложенный `AGENTS.md` может уточнять их для своей директории.
- Продукт называется **МОСТ**. `prohelper_land` — только техническое имя репозитория.
- Всегда общайся на русском языке. Пользовательские и маркетинговые тексты должны быть естественными, понятными и соответствовать бренду МОСТ.

## Git, безопасность и окружение

- Не работай напрямую в `main`: обновляй его только fast-forward, создавай отдельную ветку и передавай изменения через Pull Request.
- Не коммить, не push, не создавай PR, не merge и не deploy без отдельной явной команды. Не изменяй и не откатывай чужие файлы.
- Перед правками проверяй ветку и `git status`. Запрещены `git reset --hard`, принудительный checkout, широкое рекурсивное удаление и очистка неотслеживаемых файлов без прямого разрешения.
- Не изменяй CI/CD, GitHub Actions и deployment-конфигурацию без отдельного запроса.
- Не добавляй `.env`, ключи, токены, пароли, production-данные, локальные пути пользователя, логи, кеши, `node_modules`, `dist*`, зависимости и генерируемые артефакты.
- Не создавай SSH-ключи и не предполагай production-доступ. Диагностика production разрешена только после отдельной явной выдачи владельцем read-only доступа для конкретной задачи; операции записи и раскрытие секретов запрещены.
- Не запускай dev-сервер или production-сборку без прямой необходимости и согласования. Для документальных правок не запускай сборки и тесты.

## Архитектура React/Vite

- Используй версии React, TypeScript и Vite, закреплённые в `package.json`; major-обновления выполняй только отдельной задачей.
- Используй функциональные компоненты и hooks. Отделяй UI-компоненты от feature-контейнеров, API-клиентов, состояния и бизнес-сценариев.
- Соблюдай границы сайта, маркетинговых страниц и личного кабинета. Не связывай независимые области через скрытое глобальное состояние или прямые импорты внутренних деталей; выноси общий код только при реальном повторном использовании.
- Backend остаётся источником бизнес-правил, permissions, ownership и валидации. Клиент не должен подменять серверную защиту или исправлять контракт ad hoc workaround-ами.
- Обеспечивай responsive layout, semantic HTML, клавиатурную доступность, корректные loading/error/empty/success-состояния и отсутствие layout shifts на основных сценариях.

## API, права, переводы и контент

- Используй типизированные API-клиенты и `LandingResponse`. При несовпадении payload сначала уточни backend-контракт, а не скрывай расхождение неявной нормализацией.
- Для контрактных объектов и mapper-функций используй явные типы, `as const` и `satisfies`, где это предотвращает расширение литералов до `string`.
- Проверяй права через данные backend и существующие guards. Скрытие UI не заменяет серверную авторизацию.
- Используй существующий механизм локализации. Не показывай пользователю ключи переводов, slug-и, stack traces или технические термины; русский текст храни в корректной UTF-8.
- Сохраняй терминологию и визуальный язык МОСТ. Маркетинговые изменения не должны ухудшать SEO-метаданные, семантику, canonical/robots-настройки и доступность без явной причины.

## Проверки

- Для документации и текстов без изменения поведения не запускай сборку и тесты; проверь diff, Markdown, UTF-8 и отсутствие секретов.
- После изменений TypeScript, API-клиентов, типов, hooks или состояния запускай `npx tsc --noEmit` и ESLint только для затронутых файлов или минимального модуля.
- Для бизнес-логики, API-сценариев и сложного UI-состояния запускай целевые Vitest-тесты; для HTTP-моков используй MSW. Воспроизводимый баг покрывай регрессионным тестом.
- Не запускай `npm run build` без прямого запроса пользователя.
- В итоговом ответе перечисли изменённые файлы, выполненные проверки и причины пропуска остальных.
